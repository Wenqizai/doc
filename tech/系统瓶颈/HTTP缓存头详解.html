HTTP 缓存层：Cache-Control 与 ETag 的生产实践

读者定位：后端、前端、运维工程师（假设已了解 HTTP/1.1 基础协议）

数据来源：big-list-of-20-common-bottlenecks.md 第 39 行 — "In HTTP: headers, etags, not gzipping, etc."

声明：本文档所有性能指标均为教学示例值，非真实生产数据。

§1 核心问题：缓存层为什么能成为系统瓶颈？

缓存层的两个职责：

  • 减少回源请求数 → 节省服务器计算资源
  • 减少响应体传输量 → 节省网络带宽

当这两个目标冲突时，就可能制造反效果。

§2 Cache-Control 机制

§2.1 固定值与计时起点

浏览器收到 Cache-Control: max-age=3600，这个数字永远不变。服务器每次响应都发送同样的值。

fresh_until = Date + max-age。在 fresh_until 之前，浏览器直接使用本地缓存。

§3 Cache-Control：在哪里设置？

§3.1 四层控制点 — 后端 → Nginx → CDN

Cache-Control 的值由离浏览器最近的缓存节点决定。

§3.2 各层配置要点

后端应用（Spring Boot / Go）：

// Spring Boot — 控制器级设置，固定 max-age=30
.cacheControl(CacheControl.maxAge(30, SECONDS));

// Go — 动态 max-age：热门商品1分钟，冷门24小时
if resource.IsHot() { c.Header("Cache-Control", "max-age=60") }
else                 { c.Header("Cache-Control", "max-age=86400") }

Nginx（按 URI 类型分组）：

location ~* \.(js|css)$ { expires 7d; }                  // max-age=604800
location ~* \.(png|jpg)$  { expires 30d; }                // max-age=2592000
location /api/ { add_header Cache-Control "no-store"; }   // 不缓存

CDN 控制台（URI 匹配策略）：

URI Pattern策略
/*.{js,css}max-age=31536000, immutable
/*.htmlno-cache, must-revalidate (每次检查 ETag)
/api/*no-cache, max-age=0 (直接回源)

§4.2 ETag 生成策略对比

策略适用场景优点缺点
A. 内容 hash（Nginx 默认）静态文件语义正确（内容一致则值一致）每次请求 MD5 计算 (高 QPS CPU)
B. 后端 version + timestampAPI 接口（推荐）高效 (读两个字段)需应用层维护版本号/时间戳
C. 固定无意义值 (如 "fixed")Nginx 作 CDN 上游零 CPU 开销无法通过 304 优化
D. tag off;高频 API（推荐）零 CPU 开销由 Cache-Control 替代优化

§5 Cache-Control + ETag：最佳实践决策

资源类型推荐 Cache-ControlETag？说明
HTML 入口页 (index.html)no-cache, must-revalidate需要 (CDN)每次向 CDN 检查，通过 ETag 判断是否拿到新版
CSS / JS (文件名带 hash)max-age=31536000, immutable不需要文件名含内容 hash → 永久缓存安全
图片 / 字体 (png/jpg/svg)max-age=31536000不需要文件名可控时可长期缓存，注意 CDN purge 匹配
API 响应 (/api/*)no-store 或 max-age=0可选 (后端 hash)实时数据。条件缓存用 max-age=30 + ETag
WebSocket SSE 事件流no-cache (关闭缓存)不需要应用层处理验证，不适用 HTTP 缓存

生效规则：后端返回 no-store → 如果 CDN 启用了缓存策略，后端的 header不生效（会被覆盖）。CDN 控制台设置的策略直接决定浏览器收到的 header。

§6 生产案例一：ETag + gzip 双重开销

一个云文档编辑服务，接口返回 JSON (约 2-4KB)。平台同时开启了 gzip on; 和 Nginx 默认的 tag on;。

现象 (QPS > 3000)：

P99 (修复前)
450ms
CPU (修复前)
92%
QPS (修复前)
2,800
P99 (修复后)
85ms ↓81%
CPU (修复后)
35% ↓62%
QPS (修复后)
15,000 ↑436%

根因：Nginx 先算 MD5 做 ETag，再做 gzip。每次请求 = 完整 MD5 计算 + gzip 压缩 → 双重 CPU 负担。

// Nginx 修复方案：关闭 ETag + 对小响应跳过 gzip
location /api/documents/ {
    etag off;                      // ← 由 Cache-Control 控制缓存
    gzip on;                       // ← 只对大响应启用压缩
    gzip_min_length 1024;          // ← <1KB 的跳过 (省 CPU)
    gzip_types application/json;

§7 生产案例二：Cache-Control 滥用导致全站冷启动

前端工程师将 index.html 设置了 Cache-Control: max-age=86400 (24 小时)。

问题链：

  1. CDN 仍持有旧版 index.html (缓存未过期)。
  2. 用户刷新 → CDN 返回旧 HTML → 引用了旧版 JS。
  3. 页面完全不可用。即使新代码已部署到 CDN。

修复：主页面 Cache-Control: no-cache, must-revalidate → 每次向 CDN 检查。静态资源文件名带 hash → max-age=31536000, immutable 安全。

§8 四个黄金法则

ETag 不是免费的
高频 API 应关闭它。计算 hash、访问数据库都消耗 CPU。
Cache-Control > ETag
正确配置缓存生命周期比条件请求节省更多资源。优先配 Cache-Control。
gzip 对小响应负优化
gzip_min_length 至少 512B-1KB。小响应体不值得压缩。
CDN 与后端职责分离
后端 → CDN 不需要 ETag。ETag 只在浏览器到 CDN 层有优化价值。

§9 常见问题排查清单

⚠ 后端 CPU 高但网络流量不大

可能问题：ETag 计算 + gzip 双重开销；条件请求风暴。

验证方法：ab -c 100 压测，对比开启/关闭 ETag。

⚠ 前端更新后大量用户拿到旧版

可能问题：Cache-Control 过期太长 + CDN purge 异步延迟。

验证方法：curl -I <url> 检查 response headers。

⚠ P99 延时高、吞吐低

可能问题：gzip + etag 双重处理；小响应体不值得压缩。

验证方法：Nginx access.log + upstream_response_time 统计。

⚠ 304 状态码占比异常高 (>60%) 但后端仍跑满

可能问题：大量 HEAD 条件请求打到 Origin。

验证方法：Nginx status 304 计数或日志分析。

⚠ CDN 回源率突然激增

可能问题：Purge + ETag 同步不一致导致缓存穿透。

验证方法：CDN 监控面板回源统计。

§10 附录 A：各层配置模板

// ===== JS/CSS — 7天缓存 =====
location ~* \.(js|css)$ { expires 7d; }

// ===== 图片 / 字体 — 30天缓存 =====
location ~* \.(png|jpg|svg|woff2)$ { expires 30d; }

// ===== HTML 入口页 — 每次检查 =====
location / { add_header Cache-Control "no-cache, must-revalidate"; }

// ===== API — 强制不缓存 =====
location /api/ { add_header Cache-Control "no-store"; }

etag off;                                // 全局关闭 (推荐)
gzip on;
gzip_min_length 1024;
